# Claude Code 워크플로우 스킬을 한국어로 옮긴 포크, suberpower

Claude Code를 쓰면서 [superpowers](https://github.com/obra/superpowers)라는 플러그인을 알게 됐다. 브레인스토밍, 계획 작성, TDD, 디버깅, 코드 리뷰처럼 개발할 때 거치는 과정을 스킬로 묶어두고, Claude가 작업 성격에 맞는 스킬을 스스로 찾아 따르게 만드는 플러그인이다. [claude-sync를 만들 때](/posts/claude-sync-how-i-tested) 썼던 Spec → Plan → TDD 흐름도 이 스킬들로 굴렸다.

포크한 이유는 두 가지다.

첫째는 **공부**다. superpowers는 잘 돌아가는 것으로 알려진 워크플로우 하네스다. 스킬을 어떤 단위로 나누는지, Claude에게 어떤 강도로 지시하는지, 서브 에이전트와는 어떻게 일을 주고받는지 뜯어보면서 배우고, 그만큼 제대로 쓰고 싶었다. 그래서 한 문장씩 한국어로 옮기며 분석하기로 했다.

둘째는 **내 작업 방식에 맞게 고쳐 쓰기 위해서**다. 원본을 그대로 쓰다 보니 git worktree를 다루는 방식처럼 나와 맞지 않는 곳이 있었고, 쓰는 도중에 부딪힌 문제를 직접 고치고 싶은 곳도 생겼다.

## 이름은 suberpower

원본과 이름을 살짝 다르게 지었다. 두 플러그인을 동시에 켜면 세션이 시작될 때 스킬 안내가 두 번 주입되는데, 이름까지 같으면 어느 쪽이 로드됐는지 구분할 수가 없기 때문이다. 스킬을 부르는 이름도 `suberpower:brainstorming`처럼 원본과 갈린다.

## 번역에서 지킨 것

### 산문만 옮긴다

본문 설명은 한국어로 옮기되, 제목(`## Overview`), 기술 용어(skill, subagent, commit), 상태값(`DONE`, `BLOCKED`)은 영문 그대로 둔다. 영문 뒤에는 조사를 바로 붙인다. `dispatch하고`, `commit하세요` 같은 식이다.

### 강조의 세기를 지킨다

번역하면서 가장 신경 쓴 부분이다. 영어 지시문은 **대문자로 강도를 표현한다.** 한국어에는 대소문자가 없으니 그대로 옮기면 최상위 경고가 평범한 문장으로 내려앉고, 지시의 구속력이 실제로 약해진다.

처음에는 `CRITICAL:`을 `중요:`로 옮겼는데, 서브 에이전트가 그 지시를 덜 지키는 게 느껴져 되돌렸다. 그 뒤로는 원문의 강조 등급을 서식으로 살린다.

| 원문의 강도 | 옮기는 방식           | 예                                |
| ----------- | --------------------- | --------------------------------- |
| 최상위      | 영문 대문자 토큰 유지 | `IMPORTANT:`, `CRITICAL:`         |
| 상위        | 영문 라벨 + 대시      | `STOP - 다음 경우 escalate하세요` |
| 중간        | 굵게                  | `**반드시**`, `**절대**`          |
| 하위        | 평문                  |                                   |

예를 들어 스킬 사용 규칙의 핵심 문장은 이렇게 옮겼다. 강조 태그는 그대로 두고, `ABSOLUTELY MUST`는 힘이 빠지지 않는 "반드시"로 옮겼다.

```markdown
<!-- 원문 -->
<EXTREMELY-IMPORTANT>
If you think there is even a 1% chance a skill might apply to what you are doing, you ABSOLUTELY MUST invoke the skill.
</EXTREMELY-IMPORTANT>

<!-- suberpower -->
<EXTREMELY-IMPORTANT>
지금 하고 있는 일에 어떤 skill이 적용될 가능성이 1%라도 있다고 생각된다면, 반드시 그 skill을 호출해야 합니다.
</EXTREMELY-IMPORTANT>
```

## 포크해서 좋은 점

포크의 가장 큰 장점은 **쓰다가 불편한 곳을 기다리지 않고 바로 고칠 수 있다**는 것이다. 그중 효과가 컸던 두 가지를 소개한다.

### worktree: 작업 공간을 프로젝트 밖으로

원본의 worktree 스킬은 Claude Code에 내장된 worktree 기능에 작업을 맡긴다. 그런데 이 기능이 내 방식과 세 군데서 어긋났다.

- worktree를 프로젝트 안(`.claude/worktrees/`)에 만든다. `.gitignore` 설정에 따라 원래 저장소의 `git status`에 추적되지 않은 파일로 잡힌다.
- 기준 브랜치가 설정값에 묶여 있어, 사실상 main에 고정된 것처럼 동작한다.
- 이름을 정하지 않으면 `worktree-xxxx` 같은 무작위 이름이 붙는다.

그래서 내장 기능에 맡기지 않고, 스킬이 git으로 worktree를 직접 만들도록 다시 썼다. 흐름은 이렇다.

1. 이미 worktree 안에서 작업 중이면 새로 만들지 않는다.
2. 기준 브랜치를 묻는다. 프로젝트마다 한 번만 묻고, 답을 기억해 두었다가 다음부터는 다시 묻지 않는다.
3. 브랜치 이름을 묻는다.
4. 프로젝트 밖 전역 경로에 만든다.

```bash
project=$(basename "$(git rev-parse --show-toplevel)")
path="$HOME/.claude/suberpowers/worktrees/$project/$BRANCH_NAME"
git worktree add "$path" -b "$BRANCH_NAME" "$BASE_REF"
```

이렇게 바꾸고 나서 좋아진 점은 이렇다.

- **원래 저장소가 깨끗하게 유지된다.** worktree가 프로젝트 디렉터리 밖에 있으니 `git status`와 `git diff`에 잡힐 일이 없고, 그걸 막으려고 `.gitignore`를 건드릴 필요도 없다.
- **원하는 브랜치에서 갈라진다.** develop처럼 main이 아닌 브랜치를 기준으로 작업하는 프로젝트도 한 번만 답해두면 된다.
- **브랜치 이름만 봐도 무슨 작업인지 안다.** `fix-login`처럼 직접 붙인 이름이라, 나중에 브랜치 목록이나 PR에서 헤매지 않는다.

잃은 것도 있다. 내장 기능은 세션이 끝날 때 worktree를 남길지 지울지 물어보는데, git으로 직접 만든 worktree는 Claude Code가 추적하지 않아 그 질문을 받을 수 없다. 정리는 작업을 마무리하는 스킬이 맡도록 옮겼다.

### 리뷰어 응답 실패 버그 개선

superpowers는 물론이거니와 claude code에서는 결과물을 리뷰 서브 에이전트가 검토하는 경우가 많다. 그런데 **리뷰어가 결과를 내놓지 못하고 끝나버리는 일**이 빈번했다. 에러와 함께 끝나면 리뷰 결과가 통째로 사라졌고, 아무 통지 없이 끊기면 메인 세션은 오지 않을 결과를 하염없이 기다렸다.

원인은 [Claude Code 쪽 버그](https://github.com/anthropics/claude-code/issues/75318)였다. 오래 조용히 추론한 뒤 긴 응답을 한 번에 내보내다 연결이 끊기면, 메인 세션은 알아서 복구되지만 서브 에이전트는 그대로 죽는다. diff를 한참 읽고 긴 리뷰 보고서를 한 번에 써내는 리뷰어가 딱 그 모양이었다. 짧은 도구 호출을 자주 내보내는 구현 에이전트가 상대적으로 멀쩡했던 것도 같은 이유다.

Claude Code가 고쳐지길 기다리는 대신, 이 조건을 피하도록 리뷰어와 주고받는 방식을 바꿨다.

- **보고서를 파일에 조금씩 쓴다.** 리뷰어는 시작하자마자 보고서 파일을 만들고, 지적 사항이 하나 확정될 때마다 바로 적는다. 마지막 응답은 파일 경로, 판정, 이슈 개수만 담은 세 줄로 끝낸다.
- **끊기면 이어서 쓰게 한다.** 리뷰어가 결과 없이 끝나면 메인 세션이 먼저 보고서 파일을 읽는다. 사실상 완성돼 있으면 그대로 쓰고, 중간에 끊겼으면 새 리뷰어에게 "기록된 항목은 건너뛰고 남은 범위를 이어서 완성하라"고 맡긴다. 재시도는 두 번까지만 한다.
- **큰 변경은 나눠서 맡긴다.** 변경이 500줄이나 파일 8개를 넘으면 관련 있는 파일끼리 묶어 리뷰어를 여럿 띄운다. 각자 자기 보고서 파일만 쓰니 동시에 돌릴 수도 있다.

이렇게 바꾸고 나서 좋아진 점은 이렇다.

- **끊길 조건 자체를 피한다.** 긴 응답을 한 번에 내보내는 순간이 사라진다.
- **끊겨도 결과가 남는다.** 이미 확정한 지적은 파일에 있으니 날아가지 않는다.
- **복구 비용이 남은 만큼만 든다.** 리뷰를 처음부터 다시 시키지 않고 이어서 완성한다.
- **리뷰 한 번이 짧아진다.** 변경을 나누면 리뷰어 한 명이 볼 양이 줄어 도중에 실패할 가능성도 낮아진다.

보고서 파일은 worktree와 같은 이유로 프로젝트 밖(`~/.claude/suberpowers/reviews/`)에 둔다. 저장소 안에 쓰면 `git status`에 잡혀서, 리뷰어가 그 파일을 "요청하지 않은 추가 파일"로 오해할 수 있기 때문이다. 나눠서 리뷰하면 그룹 사이에 걸친 문제는 어느 리뷰어도 보지 못하는데, 그 부분은 메인 세션이 보고서들을 모아 판정할 때 직접 확인하게 했다.

마지막으로, 이런 우회책은 버그가 고쳐지면 걷어내야 한다. 그래서 우회책마다 원인이 된 Claude Code 이슈 번호를 적어두고, GitHub Actions가 매주 그 이슈 상태를 확인하게 했다. 이슈가 닫히면 "이제 이 우회책을 걷어낼지 검토하라"는 이슈가 저장소에 자동으로 올라온다. 임시로 넣은 코드가 영원히 남지 않게 하기 위해서다.

## 원본과 멀어지지 않기

포크를 유지하는 데서 가장 걱정되는 건 **원본의 변경을 가져올 때**다. 원본은 계속 업데이트되는데, 그 변경을 번역본 위에 덮다 보면 포크가 일부러 다르게 만든 부분이 조용히 사라지기 쉽다. worktree 스킬을 다시 원본 방식으로 덮어버리는 식이다.

그래서 "일부러 원본과 다르게 둔 곳"을 목록으로 만들어 두었다. 이름 변경, worktree 재작성, 번역 규칙, 강조 계층 같은 항목이 지금 일곱 개 있고, 항목마다 원본이 바뀌었을 때 어떻게 할지 정해두었다.

- **절대 덮어쓰지 않는다**: 이름 변경처럼 포크의 정체성인 것
- **사람이 읽고 골라서 반영한다**: worktree 스킬처럼 통째로 다시 쓴 것
- **가져오되 포크 규칙으로 바꿔서 반영한다**: 스킬 설명(description) 규칙처럼 형식만 맞추면 되는 것

그리고 이 목록이 지켜지는지 스크립트로 검사한다. 문자열이나 경로처럼 기계로 셀 수 있는 건 스크립트가 바로 판정한다. 번역의 톤처럼 읽어봐야 아는 건 스크립트가 확인할 질문을 내놓고, **사람이 확인했다고 표시하기 전에는 통과시키지 않는다.**

```bash
./scripts/check-divergence.sh          # 평소
./scripts/check-divergence.sh --sync   # 원본을 가져온 뒤, 사람의 확인까지 요구
```

기계로 못 재는 항목일수록 조용히 사라지기 쉬운데, 이렇게 해두면 적어도 확인을 건너뛸 수는 없다.

## 설치

```bash
claude plugin marketplace add june20516/suberpower
claude plugin install suberpower@suberpower
```

원본 superpowers와 동시에 켜면 세션 시작 안내가 중복되니, 둘 중 하나만 쓰는 게 좋다.

## 마무리

번역은 단어를 옮기는 일이라고 생각했는데, 지시문을 옮기는 건 **강도를 옮기는 일**에 가까웠다. 그리고 한 문장씩 옮기며 뜯어본 덕분에, 불편한 곳이 생겼을 때 어디를 어떻게 고치면 되는지도 보이기 시작했다.

설치 명령과 저장소 링크는 [Lab의 Claude Tools](/lab/claude-tools)에도 모아뒀고, 코드는 [GitHub](https://github.com/june20516/suberpower)에서 볼 수 있다.
