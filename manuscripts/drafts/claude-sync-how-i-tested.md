# claude-sync를 만든 방식: 테스트 1,269개와 줄어든 검증 시간

[이전 글](/posts/claude-sync-introduce)에서 Claude Code 설정을 기기 간에 동기화하는 플러그인 claude-sync를 소개했다. 이 도구는 남의 기기에서 온 변경을 받아 **로컬 설정 파일을 덮어쓰거나 지운다.** 한 번 잘못 판정하면 다른 기기에서 공들인 설정이 조용히 사라진다. 그래서 "대충 돌아가는" 수준으로는 내놓을 수 없었고, 결과적으로 테스트가 1,269개(v3.1.2 기준)까지 늘었다.

이 글은 그 테스트들을 어떻게 만들었고, 검증이 오히려 발목을 잡기 시작했을 때 어떻게 줄였는지에 대한 기록이다.

## 작업 방식

### spec → plan → TDD

큰 변경은 늘 설계 문서(spec)에서 시작했다. spec이 정해지면 그것을 task 단위의 구현 계획(plan)으로 쪼개고, task마다 순서를 고정했다.

1. 실패하는 테스트를 쓴다
2. 실제로 실패하는지 돌려본다
3. 구현한다
4. 통과하는지 돌려본다
5. 코드를 일부러 망가뜨려서, 방금 쓴 테스트가 그걸 잡는지 확인한다 (변조 확인)
6. 커밋한다

이 흐름은 내가 한국어로 포크해서 쓰는 워크플로우 스킬 모음(suberpower)의 brainstorming → writing-plans → subagent-driven-development를 그대로 따른 것이다.

### subagent에게 나눠 맡기기

구현은 task마다 새로 띄운 subagent가 맡고, 결과물은 다른 subagent가 두 번 리뷰했다. 한 번은 spec대로 만들었는지, 한 번은 코드 품질이 괜찮은지.

plan이 커지면서 요령도 생겼다. plan 본문이 5,300줄을 넘자 subagent에게 통째로 주지 않고, 공통 규칙 파일과 그 task 파일만 잘라서 건넸다. 세션의 컨텍스트가 차오르면 억지로 이어가지 않고 인계 문서를 남겼다. 한 인계 문서에는 이렇게 적혀 있다.

> 세션이 86%였다. 재료를 쓰는 대신 남겼다.

### 사람이 쥐고 있던 것

push, 머지, 태그, 배포는 전부 내가 직접 했다. 애매한 판단도 subagent가 알아서 정하지 않고 나에게 물었다.

재밌는 제약도 하나 있었다. 개발하던 기기에는 구버전(2.0.0) 플러그인이 캐시되어 있어서, 여기서 `/sync-backup`을 실행하면 백업 레포가 망가질 수 있었다. 그래서 몇 개의 plan을 진행하는 동안 **세 스킬을 한 번도 실제로 실행하지 않았다.** 스킬의 동작은 테스트로 지켰고, 실제 기기 확인은 릴리즈 때 체크리스트를 따라 따로 했다.

## 어떤 테스트를 했나

첫 테스트는 2026년 6월에 쓴 6개였다. v3.1.2 시점에는 1,269개가 됐다. 전부 소개하기엔 많으니 성격이 다른 다섯 가지만 추렸다.

### 여러 기기가 번갈아 쓰는 시나리오

동기화 도구의 결함은 대개 한 기기 안에서는 드러나지 않는다. 그래서 임시 HOME 디렉토리를 기기처럼 여러 개 만들고, 같은 레포를 공유한 채 backup과 restore를 번갈아 실행하는 테스트를 만들었다. `claude mcp add` 같은 CLI 명령만 흉내 내고, 나머지 단계는 전부 실제 스크립트를 호출한다.

backup만 반복하는 테스트로는 부족했다. 사용자가 restore에서 선택지를 고른 **뒤의** 상태 변화가 드러나지 않기 때문이다. 실제로 base 갱신 규칙 하나가 빠진 결함도 backup 반복 테스트는 전부 통과했다.

### 같은 입력을 반복해도 발산하지 않는지

[이전 글](/posts/claude-sync-introduce)의 "서버가 사라진" 결함에서 나온 테스트다. 백업 한 번의 판정표를 100% 덮은 테스트는 전부 통과했지만, 두 번째 백업에서 다른 기기의 서버가 사라졌다. 그 뒤로는 같은 입력으로 백업을 여러 번 돌려 **결과가 한곳에 수렴하는지(고정점)** 확인한다. 판정표의 시나리오 열 개는 MCP 서버, 그리고 플러그인 쪽 두 섹션까지 세 어댑터가 함께 쓴다.

### SKILL.md 문장도 코드처럼 검사

Claude Code 스킬에서 실제로 복원을 실행하는 건 Python이 아니라 `SKILL.md`의 **문장**이다. 모델이 그 문장을 읽고 명령을 실행한다. 그런데 테스트는 그 문장이 아니라 같은 동작을 Python으로 다시 구현한 쪽을 검사하고 있었다.

그래서 문장 쪽을 일부러 망가뜨려 봤다. `SKILL.md` 문장에서 이름을 바꿔치기하는 변조 6종 중 **5종이 살아남았고,** 살아남은 다섯은 모두 복원 절차의 문장이었다. 같은 이름을 스크립트 쪽에서 바꾸면 테스트 40개가 실패하는데, 문장에서 바꾸면 0개였다. 그 뒤로 `SKILL.md`의 절차 문장이 스크립트가 실제로 내놓는 키를 부르고 있는지 대조하는 테스트를 따로 두었다.

### 셸 블록은 실제 셸로 실행

`SKILL.md`에는 bash 블록도 들어 있다. 처음에는 그 블록의 사본을 검사했는데, 이게 가짜 안전망이었다. 최신 버전 디렉토리를 고르는 `sort -V | tail -1`을 아무거나 고르는 `head -1`로 바꿔도 검사 13개가 전부 통과했다.

그래서 `SKILL.md`에서 블록을 꺼내 **실제로 실행하도록** 바꿨는데, 그래도 구멍이 남았다. `head -1`은 `find`의 첫 출력을 고르는데, 테스트 픽스처에서는 우연히 최고 버전이 맨 앞에 나와서 둘이 구별되지 않았던 것이다. 지금은 픽스처 버전을 이렇게 둔다.

```python
VERSIONS = ["2.0.0", "3.0.0", "3.9.0", "3.10.0", "12.0.0"]
```

숫자로 최대인 `12.0.0`이 `find`의 첫 출력도, 사전순 최대도 아니고, `3.9.0`과 `3.10.0`이 함께 있어 자릿수 비교까지 잡는다. 이전 글에서 소개한 `mapfile` 사건도 같은 계열이다. 텍스트만 검사하던 블록을 bash와 zsh에서 실제로 돌리게 바꾼 뒤에야 막혔다.

### 변조 테스트: 테스트를 테스트하기

테스트가 통과한다고 해서 그 테스트가 무언가를 지키고 있다는 보장은 없다. 그래서 코드를 일부러 망가뜨린 복사본에서 전체 스위트를 돌리는 변조(mutation) 테스트를 붙였다. 테스트가 실패하면 `CAUGHT`, 그래도 통과하면 `SURVIVED`다. 변조 하나는 이렇게 적는다.

```json
{
  "id": "M1",
  "desc": "축1 훅 호출 계약 — 트리 인자를 무시하고 다시 로컬을 걷는다",
  "file": "plugins/claude-sync/skills/sync-backup/scripts/generate_metadata.py",
  "old": "    for rel in sorted(ss.iter_synced_relpaths(tree_root)):",
  "new": "    for rel in sorted(ss.iter_synced_relpaths(os.path.expanduser(\"~/.claude\"))):"
}
```

변조를 돌리면서 배운 규칙이 몇 가지 있다.

- **아무것도 바꾸지 않은 대조군을 먼저 돌린다.** 대조군부터 실패하는 상태라면 나머지 판정은 전부 믿을 수 없다.
- **치환이 안 먹은 것(`APPLY_FAIL`)을 통과(`SURVIVED`)로 읽지 않는다.** 이름이 바뀐 코드에서는 예전 변조가 아무것도 바꾸지 못하고 조용히 초록이 된다.
- **`SURVIVED`라고 다 구멍은 아니다.** 오늘의 동작과 완전히 같은 결과를 내는 등가 변조도 있다.

## 검증이 느려졌다

테스트를 촘촘히 쌓을수록 새로운 문제가 생겼다. **검증 자체가 느려진 것이다.**

한 plan의 첫 task는 1시간 53분이 걸렸다. 프로덕션 코드는 102줄 추가, 22줄 삭제였다. 시간은 subagent 실행 약 100분(구현 48분, 리뷰어 다섯 번 52분)과 그 사이 조율 12분으로 나뉘었다. 리뷰를 라운드별로 다시 보니 이런 모양이었다.

| 라운드 | 프로덕션 로직 결함 | 그 외 |
| --- | --- | --- |
| spec 리뷰 1 | 0 | 문서 서술 오류 2 |
| spec 리뷰 2 | 0 | 아무것도 검사하지 않는 단정 1 |
| spec 리뷰 3 | 0 | 0 |
| quality 리뷰 1 | 0 | 테스트 공백 1, 틀린 주석 1, 사소한 것 5 |
| quality 리뷰 2 | 0 | 사소한 것 1 |

다섯 라운드 내내 로직 결함은 0건이었다. 당시 기록에 적은 문장이 이 상황을 그대로 요약한다.

> 로직은 첫 시도에 수렴했다. 수렴하지 않은 것은 「증명」이다.

## 검증을 줄인 방법

그래서 이후 task에 공통으로 적용할 규칙 세 가지를 plan에 넣었다.

### 어디서 멈출지 정했다

검증을 끝내는 기준을 명시했다.

1. **커버리지**: 변조를 다섯 축(훅 호출 계약, 축 분리, `{}`와 `None`의 구분, I/O 층, 입력 축)에 하나 이상씩 세우고, 전부 `CAUGHT`면 끝낸다.
2. **깊이**: 테스트는 자기 입력이 비면 스스로 실패하게 만들고, **테스트를 지키는 테스트는 만들지 않는다.**
3. **라운드**: 위 둘을 채우고 로직 결함이 0건이면 리뷰를 종료한다.

첫 task에서 리뷰가 잡은 실제 결함은 다섯 축 중 첫 번째 축이었는데, 그 task의 변조 목록에는 그 축이 없었다. 처음부터 다섯 축을 채웠다면 첫 라운드에 나왔고 리뷰 두 라운드가 줄었을 것이다.

### 위험한 곳만 깊게 본다

검증 강도는 "코드냐 문서냐"가 아니라 **"여기서 조용히 틀리면 되돌릴 수 없는 행동이 나가는가"** 로 나눴다. 이 프로젝트에서는 `SKILL.md` 문장이 곧 실행물이라, 문서로 분류하면 가장 위험한 곳이 가장 헐거워지기 때문이다.

| 등급 | 해당 | 검증 |
| --- | --- | --- |
| 중 | 판정 로직, 쓰기 경로, 사용자에게 행동을 권하는 문장 | 변조 전부(다섯 축) + 리뷰 2단계 |
| 경 | 보고 형식, 사실을 적는 docstring, spec 서술 | grep 전수 확인 + 리뷰 1단계 |
| 미 | 이름, 가독성, 주석 다듬기 | 리뷰 없이 커밋 |

### 변조는 의미 있는 곳에만, 리뷰어 대신

리뷰 기록을 보니 리뷰어가 찾아낸 가치는 전부 **리뷰어가 새로 고안한 변조**에서 나왔다. 구현 쪽이 이미 돌린 변조를 다시 돌린 데서는 새 정보가 하나도 없었다. 그래서 이미 `CAUGHT`로 확인된 변조는 다시 돌리지 않고, 새 변조만 의미 있는 축에 더하기로 했다.

나중에는 리뷰 subagent를 아예 빼고 변조만 돌린 task들도 있었다. 변조 46벌 중 6벌이 실제 테스트 공백을 찾았고, 리뷰가 잡던 것과 같은 종류였다. 기록에는 "변조가 리뷰어보다 싸고 자주 맞았다"고 적었다.

한 가지 짚어두면, 변조 하나는 여전히 전체 스위트를 돈다. 줄인 것은 변조를 돌리는 범위가 아니라 **만드는 변조의 개수**다.

### 결과

| | 첫 task | 다음 두 task | 5번째 task | 6번째 task |
| --- | --- | --- | --- | --- |
| task당 시간 | 100분 | **30분** | 55분 | 60분 |
| spec 리뷰 라운드 | 3 | 1 | 2 | 2 |

task당 시간이 100분에서 30분으로 줄었다. 5·6번째 task에서 다시 늘어난 건 `SKILL.md` 문장을 고치는 task라 리뷰가 실제 결함을 계속 찾았기 때문이다. 경고 문단 몇 줄 아래에서 정반대 내용을 말하던 문장처럼, 사용자에게 잘못된 안내가 나갈 뻔한 오류들이었다. 이런 라운드는 낭비가 아니었다.

## 테스트를 돌리는 습관

규칙과 별개로, 테스트를 돌리는 습관도 바뀌었다.

### 작업 중에는 필요한 테스트만

처음에는 뭘 고치든 전체 스위트를 돌렸다. 테스트가 늘어나면서 task 중간에 돌리는 테스트는 이번 변경과 관련된 것으로 좁혔고, plan의 각 단계에도 아예 그렇게 적었다.

```bash
# 실패 확인 — 이번 변경과 관련된 테스트만
uv run --with pytest pytest plugins/claude-sync/tests/test_reconcile.py -q -k "reject_bucket or splits_reject or excluded_file"

# 통과 확인 — 전체
uv run --with pytest pytest plugins/claude-sync/tests -q
```

### task 끝에서는 전체를 돌린다

좁혀 돌리기만 하면 놓치는 게 생긴다. 리뷰 중에 가짜 어댑터를 붙이고 코어 규칙 하나("보류 중인 키는 레포 값을 그대로 싣는다")를 지우는 변조를 넣어 본 적이 있다. 상태 기계 테스트 파일만 돌리면 20개가 그대로 통과했다. 전체 스위트에서는 다른 파일의 테스트 2개가 그걸 잡았다.

그래서 작업 중에는 좁게 돌리되, task를 닫기 전에는 반드시 전체를 돌렸다.

## 마무리

테스트를 많이 쓰는 것까지는 어렵지 않았다. 어려웠던 건 그 테스트가 정말 뭔가를 지키는지 확인하는 일과, **어디서 확인을 멈출지** 정하는 일이었다. 검증에도 비용이 있고, 그 비용을 위험도에 맞게 나눠 쓰는 것까지가 검증이었다.

claude-sync가 무엇을 하는 도구인지는 [이전 글](/posts/claude-sync-introduce)에, 설치 명령과 저장소 링크는 [Lab의 Claude Tools](/lab/claude-tools)에 있다. 코드와 테스트는 [GitHub](https://github.com/june20516/claude-sync)에서 볼 수 있다.
